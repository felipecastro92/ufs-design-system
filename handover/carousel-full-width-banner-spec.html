Carousel — Full Width Banner

A full-bleed promo carousel — 40% dark text panel + 60% image, moving as one rigid slide. Desktop directional transition, mobile swipeable filmstrip, full RTL/i18n support — documented for implementation.

Source

Overview

Full Component Preview

A single <section class="ufs-fw-banner"> serving as the page's hero: a full-bleed carousel where each slide bundles its 40% dark text panel and 60% image into one rigid unit — panel and image always move together as a single block, never as two independently-clipped lanes. Every preview on this page is the real, working component — not a screenshot — so the arrows, dots, swipe and transitions below are fully interactive.

ℹ️
Manual navigation only (arrows, dots, keyboard, swipe) — no autoplay. Sidesteps WCAG 2.2.2 (Pause, Stop, Hide) entirely, since nothing moves on its own. Slides cycle (wrap at both ends), unlike the Flex Carousel above it on the page, which stops at its bounds — a loop reads better for a slideshow-style promo banner than a bounded track does.
🧱
One rigid slide, not two lanes
Panel + image are one .ufs-fw-banner__slide unit. Arrows and dots live outside the sliding track as persistent overlay chrome, so they never move.
👆
Real swipe on mobile
Below 768px, arrows disappear and slides sit in a touch-draggable filmstrip — direction-locked so it doesn't fight the page's own vertical scroll.
🌍
Fully localised
Every string — badge, title, description, CTA, arrow labels — resolves through data-i18n. Logical CSS properties mirror the whole layout automatically under dir="rtl".

Structure

Anatomy

One .ufs-fw-banner root containing a .ufs-fw-banner__track (the sliding/draggable layer) with N .ufs-fw-banner__slide children, each holding a .ufs-fw-banner__panel (badge, title, description, CTA) and a .ufs-fw-banner__image. Arrows, the scrim, dots and the screen-reader status line sit outside the track, as direct children of the root — persistent chrome that never moves.

Root — .ufs-fw-banner
Clips everything (overflow: hidden) and establishes the positioning context for the overlay arrows/dots. Fixed 600px tall on desktop; height: auto on mobile, where each slide's own content determines height.
Track — .ufs-fw-banner__track
Deliberately has no overflow: hidden of its own — see the notice below. On mobile this becomes the element that physically translates during swipe/snap.
⚠️
Don't add overflow: hidden back onto the track. It was there originally and caused a real, confirmed bug: pairing overflow: hidden with an animated transform on the same element made revealed slides fail to paint on mobile — the DOM/computed styles were correct, but the browser never rendered the content, even though layout was right. The root .ufs-fw-banner already clips everything, so the track doesn't need its own clip boundary. Keep the "clip" and "transform" responsibilities on different elements.
Slide — .ufs-fw-banner__slide
Bundles panel + image into one unit. position: absolute; inset: 0 on desktop (each slide independently transforms for enter/exit); position: relative, a plain flex-row item at flex: 0 0 100% on mobile (the whole track translates instead — see Slide Transition and Swipe below for why the mechanism differs per breakpoint).

Panel — .ufs-fw-banner__panel
Dark (--color-brand-dark), 40% width on desktop via flex: 0 0 40%. Left/start padding is 120px to clear the persistent prev arrow floating over it. On mobile the same flex: 0 0 40% would be read as a height basis instead (the slide switches to flex-direction: column) — overridden to flex: 1 1 auto there. Contains, in order: badge, title (text-h2), description (text-body-sm), CTA (.btn.btn-primary).
Image — .ufs-fw-banner__image
A clipping box, 60% width on desktop, fixed 240px tall on mobile (stacked above the panel via order: 1). The actual background-image div (not <img>) is a nested .ufs-fw-banner__image-media that fills it via position: absolute; inset: 0 — kept separate from the clipping box so the desktop-only Ken Burns zoom (transform: scale(1 → 1.08) over 8s while the slide is .is-active) can't bleed into the panel next to it. A transform escapes its own box and is only ever clipped by an ancestor's overflow: hidden, never by overflow:hidden on itself.

Structure

Content Length

All 3 example slides on this page were checked against the limits below. The description is the only field with a real, code-enforced cap — mobile clamps it to 3 lines with an ellipsis (-webkit-line-clamp: 3). Everything else here is content-authoring guidance, not enforced in code.

Badge≤ 20 characterssingle-line pill, doesn't wrap gracefully
Title≤ 60 characterswraps freely at 26ch/line on desktop — keeps it to ~3 lines
Description≤ 150 charactersfits the mobile 3-line clamp without truncating
CTA label≤ 25 charactersshort, action-led — avoid wrapping inside the button
⚠️
Description is the one field that actually truncates. Go over ~150 characters and mobile will visibly cut it off with an ellipsis after line 3 — desktop has no clamp, so the same copy reads in full there, meaning a slide can look complete on desktop and truncated on mobile. Write to the mobile limit, not the desktop one. Title, badge and CTA don't truncate; going long there risks wrapping (title), an awkward pill shape (badge), or an oversized/wrapped button (CTA) rather than lost content — but all three still affect how tall the slide reads once every slide is stretched to match the tallest one.
💡
The 3 example slides sit at 129, 137 and 100 characters of description — all comfortably under the 150-character mobile limit, confirmed not to truncate. Slide 1's title (59 characters, "Descubra a experiência digital do Menus do Futuro Vol. 4.") is the longest example and wraps to 3 lines on both breakpoints without issue.
Behaviour

Slide Transition — Desktop

Each .ufs-fw-banner__slide is position: absolute; inset: 0, independently transformed for enter/exit — the incoming slide enters from the side that matches the navigation direction (Next → from the right, Prev → from the left, or the shorter path for a dot jump), while the outgoing slide exits the opposite way. Because panel + image live inside the same slide element, they always move as one indivisible block — never as two separately-clipped 40%/60% lanes.

The enter/exit class dance
Four transform states, toggled by goTo() in JS; CSS just defines what each one looks like.
.is-enter-righttranslateX(100%)incoming slide, Next pressed
.is-enter-lefttranslateX(-100%)incoming slide, Prev pressed
.is-exit-lefttranslateX(-100%)outgoing slide, Next pressed
.is-exit-righttranslateX(100%)outgoing slide, Prev pressed
Sequence per navigation
1) Outgoing slide loses .is-active. 2) Incoming slide gets .is-notransition + its enter class (jumps instantly off-screen, no animation) — a forced reflow (void newEl.offsetWidth) locks that starting position in before the next step. 3) .is-notransition is removed. 4) On the next animation frame, the enter class comes off and .is-active goes on the incoming slide, while the exit class goes on the outgoing one — both now animate toward/away from center over 0.5s. 5) After 550ms, all enter/exit classes are cleared and animating unlocks.
💡
The forced reflow in step 2 matters: without it, the browser can coalesce "jump off-screen" and "remove the no-transition guard" into a single style recalculation and skip the jump entirely, so the slide would visibly animate in from its old position instead of snapping off-screen first. The same "toggle a property, force a reflow, then change the animated property" pattern shows up again in the mobile track code below — it's the fix for a whole category of "browser skips animating to the new value" bugs, not a one-off hack.
JS — goTo(), desktop branch
var enterClass = direction === 'next' ? 'is-enter-right' : 'is-enter-left';
var exitClass  = direction === 'next' ? 'is-exit-left'   : 'is-exit-right';
animating = true;

var oldEl = slides[oldIndex], newEl = slides[newIndex];
oldEl.classList.remove('is-active');
newEl.classList.add('is-notransition', enterClass);
void newEl.offsetWidth; /* force reflow so the entry position applies before we animate away from it */
newEl.classList.remove('is-notransition');

requestAnimationFrame(function() {
  newEl.classList.remove(enterClass);
  newEl.classList.add('is-active');
  oldEl.classList.add(exitClass);
});

clearTimeout(slideTimer);
slideTimer = setTimeout(function() {
  slides.forEach(function(el) { el.classList.remove('is-enter-right', 'is-enter-left', 'is-exit-left', 'is-exit-right'); });
  animating = false;
}, 550);
Behaviour

Swipe — Mobile

Below 768px, arrows are hidden and the mechanism changes entirely: instead of each slide independently transforming, all slides sit side by side in the track as a classic swipeable filmstrip, and the track itself translates — dragged 1:1 with the finger, then snapped to the nearest slide (or bounced back) past a 15%-of-width distance threshold.

Direction locking
Swipe handling doesn't assume every touch on the track is a horizontal swipe — that would fight the page's own vertical scroll. The first ~6px of movement decides intent:
touchstart
→
movement < 6px?
→
wait, do nothing yet
movement ≥ 6px
→
|dx| ≤ |dy|?
→
vertical — hand off to native scroll
movement ≥ 6px
→
|dx| > |dy|?
→
locked horizontal — drag the track, preventDefault()
Why preventDefault() only after locking
Calling preventDefault() only once a gesture is confirmed horizontal — not on every touchmove from the start — lets iOS's own scroll recognizer fully hand off the touch instead of both systems fighting over the same gesture mid-drag. touchmove is registered { passive: false } specifically so preventDefault() is allowed to run at all (Safari ignores it on a passive listener).
Threshold & snap
Snap threshold15% of track widthdrag past this → advances to next/prev slide
Under thresholdsetMobileTrack(true)bounces back to the current slide, animated
Transform mathpure px, not calc(%+px)-activeIndex * offsetWidth + delta — one unit throughout
⚠️
Touch events, not Pointer Events + setPointerCapture. An earlier version used unified Pointer Events with setPointerCapture() for reliable dragging outside the element's bounds — this has a confirmed iOS Safari bug where capturing a touch pointer silently breaks the next gesture on the same element (first swipe works, everything after is dead). Plain touchstart/touchmove/touchend/touchcancel is the reliable, battle-tested approach. Mouse drag (for testing in a resized desktop viewport with no real touchscreen) is wired separately via mousedown + window-level mousemove/mouseup, which needs no capture at all.
⚠️
Don't add will-change: transform to the track. It was tried as a fix for an unrelated paint bug and made things worse: on-device testing on iOS Safari showed it causes touchstart to stop being delivered to the track entirely, right after the first swipe's transition finishes — a confirmed, reproducible input bug, not a rendering one. Removing it alone looked like it fixed swiping, but didn't — see below.
⚠️
The empty document-level touchstart listener is required, not leftover debug code. It was added while diagnosing the freeze above and looked like pure instrumentation, so an earlier pass deleted it as cleanup — which brought the freeze straight back, confirmed on-device. Without a capture-phase touchstart listener registered on document, iOS Safari stops delivering touchstart to .track after the first swipe's transition finishes, even with will-change removed. Keep the no-op listener; don't mistake it for dead code.
JS — drag handlers
/* Load-bearing — see notice above. Not diagnostic logging. */
document.addEventListener('touchstart', function() {}, { capture: true, passive: true });

function moveDrag(x, y, evt) {
  if (!dragging) return;
  if (!dragLocked) {
    var dx = x - dragStartX, dy = y - dragStartY;
    if (Math.abs(dx) < 6 && Math.abs(dy) < 6) return; /* not enough movement yet to know intent */
    if (Math.abs(dx) <= Math.abs(dy)) { dragging = false; return; } /* vertical — hand off to native scroll */
    dragLocked = true;
    track.style.transition = 'none';
    void track.offsetWidth;
  }
  if (evt && evt.cancelable) evt.preventDefault();
  dragCurrentX = x;
  var deltaPx = dragCurrentX - dragStartX;
  track.style.transform = 'translateX(' + (-activeIndex * track.offsetWidth + deltaPx) + 'px)';
}

track.addEventListener('touchstart', function(e) { startDrag(e.touches[0].clientX, e.touches[0].clientY, false); }, { passive: true });
track.addEventListener('touchmove', function(e) { moveDrag(e.touches[0].clientX, e.touches[0].clientY, e); }, { passive: false });
track.addEventListener('touchend', endDrag);
track.addEventListener('touchcancel', endDrag);
Behaviour

Uniform Slide Height

On mobile, all 3 slides report the same total height — the track's default align-items: stretch stretches every .ufs-fw-banner__slide to match the tallest one's natural content height, so a short slide's panel doesn't look truncated or cramped at the bottom when you swipe to it, and swiping between slides doesn't jump the whole banner's height around.

⚠️
The panel needs flex: 1 1 auto on mobile, not the desktop flex: 0 0 40%. That value is a width basis, meant for the desktop side-by-side layout. Once the mobile media query switches the slide to flex-direction: column, the same property is read as a height basis instead — producing inconsistent, unpredictable panel heights per slide. flex: 1 1 auto lets the panel simply fill whatever space is left under the fixed 240px image, which is what actually makes the stretch-to-tallest-slide behavior work correctly.
CSS
/* align-items:stretch is the flex default — not set explicitly, but this
   is what makes every .slide match the tallest one's natural height */
.ufs-fw-banner__track { display: flex; … }

.ufs-fw-banner__image { order: 1; flex: none; height: 240px; } /* fixed */
.ufs-fw-banner__panel { order: 2; flex: 1 1 auto; … } /* fills the rest */
Behaviour

Badge — Mobile Positioning

On mobile only, the badge lifts out of the panel's normal flow and floats over the top-left of the image instead — position: absolute; top: var(--space-6) — with a darker, more opaque treatment (rgba(0,0,0,0.7) background, rgba(255,255,255,0.5) border) than its desktop appearance, since it now sits on top of a photograph rather than the flat dark panel.

Anchoring — why the slide needs position: relative
The badge is a child of .panel, but positioning it relative to just the panel would confine it to the panel's own box (below the image on mobile). It needs to anchor to the whole slide — image + panel together — so .ufs-fw-banner__slide gets position: relative on mobile specifically for this (it's position: absolute on desktop already, for the enter/exit transitions, and doesn't need the override there).

Behaviour

Image Zoom — Desktop

On desktop only, each slide's photo slowly scales from 1.0 to 1.08 over 8 seconds (Ken Burns-style) once the slide becomes active — see any slide in the Full Component Preview above. The animation restarts every time a slide (re)becomes active, and holds at the zoomed-in scale once it finishes rather than resetting or looping.

Why the image needs an inner wrapper
.ufs-fw-banner__image is a fixed-size clipping box (position: relative; overflow: hidden); the photo itself lives on a nested .ufs-fw-banner__image-media that gets scaled via transform. A CSS transform escapes its own box and is only ever clipped by an ancestor's overflow: hidden — never by overflow:hidden on the transformed element itself — so scaling .ufs-fw-banner__image directly would bleed the zoomed photo into the panel next to it.
CSS
.ufs-fw-banner__image { position: relative; overflow: hidden; } /* clips */
.ufs-fw-banner__image-media { position: absolute; inset: 0; } /* paints + scales */

@keyframes ufs-fw-banner-zoom { from { transform: scale(1); } to { transform: scale(1.08); } }

@media (min-width: 769px) {
  .ufs-fw-banner__slide.is-active .ufs-fw-banner__image-media {
    animation: ufs-fw-banner-zoom 8s ease-out forwards;
  }
}
@media (prefers-reduced-motion: reduce) {
  .ufs-fw-banner__image-media { animation: none; }
}
💡
Re-adding .is-active to a slide that had it removed naturally restarts the CSS animation from 0% — no JS timing hooks needed, the browser treats it as a fresh animation. animation-fill-mode: forwards is what makes it hold at scale(1.08) once the 8s finishes instead of snapping back to 1.0.

Reused Components

Arrows & Pagination

Both controls are reused verbatim from the Flex Carousel — same .ufs-carousel-arrow/.ufs-carousel-dot markup and JS, no new component CSS written. They read colour from --carousel-* custom properties, so adapting them here is a pure token swap.

Variants

Single Slide

When a .ufs-fw-banner instance contains exactly one .ufs-fw-banner__slide, arrows and pagination dots are not rendered — there's nowhere to navigate to, so showing controls that do nothing would be misleading rather than just unnecessary. This is derived automatically from the actual slide count in the DOM at init time; no extra class or flag needs to be added by hand.

JS — init, single-slide check
/* Single-slide instances have nothing to navigate to — arrows and
   pagination would just be dead controls, so skip creating them
   entirely rather than rendering a lone, permanently-active dot
   and a pair of do-nothing arrow buttons. */
var singleSlide = slides.length <= 1;
if (singleSlide) {
  if (prevBtn) prevBtn.style.display = 'none';
  if (nextBtn) nextBtn.style.display = 'none';
} else {
  slides.forEach(function(_, i) {
    /* …creates one .ufs-carousel-dot per slide, as before */
  });
}
💡
The dots wrapper is left in the DOM either way — with zero children it naturally collapses to 0×0 (.ufs-carousel-dots has no padding or min-size), so no extra hiding rule was needed there. Only the arrow buttons needed an explicit display: none, since as real buttons they'd otherwise keep their own footprint and remain focusable/clickable even with nothing to do.
Internationalisation

i18n & RTL

Every piece of copy — badge, title, description, CTA, the section's own aria-label, and both arrow labels — resolves through data-i18n/data-i18n-aria, matching the announcement banner, breadcrumb, header and footer. The layout mirrors automatically under dir="rtl": the 40%/60% panel/image split is a plain flex row (reverses on its own), and the one physical measurement that matters — the panel's 120px arrow clearance — uses padding-inline-start rather than padding-left, so it follows the prev arrow (itself positioned via inset-inline-start) to whichever side is logically "start" in the current direction.

What flips (and how)
Panel / image orderautomatic (flex row)image renders on the left, panel on the right — no flex-direction: row-reverse needed
Prev / Next arrowsinset-inline-start / -endprev lands on the visual right (inside panel), next on the visual left (over image)
