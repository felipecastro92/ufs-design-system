Announcement Banner

Dismissable, inset content-flow card for site-wide or page-level messages — optional live countdown, optional link, and a desktop sentence that stacks into individual lines + a button on mobile.

Overview

Full Component Preview

A single <div class="ufs-ann-banner"> — an inset, rounded, bordered card placed in the page's content flow (e.g. directly below the header, above the breadcrumb). Composed of an optional countdown, a title/text/link "sentence," and a close button. Dismissing it is session-only: it reappears on the next page load.

Structure

Anatomy

Four parts, three of them optional: an optional countdown row, a content paragraph (.ufs-ann-banner__title is optional, .ufs-ann-banner__text is the baseline, .ufs-ann-banner__link is optional), and a required close button.

Content Length

The desktop row is a fixed 64px tall single line — title, text and link all have to fit on it without wrapping to a second line or crowding the countdown/close button. The limit is tighter when a countdown is present, since it already claims a fixed block of horizontal space before the sentence even starts.

With countdown130 characterstitle + text + link combined, spaces included
Without countdown170 characterstitle + text + link combined, spaces included
⚠️
This is a content-authoring rule, not enforced in code. Nothing truncates or validates length automatically — check the combined character count (title + description + link, spaces included) against the applicable limit above before publishing a banner. Going over doesn't break anything outright, but risks the sentence wrapping to a second line on desktop (the row's fixed 64px height won't grow to fit it) or, on mobile, an unusually tall stacked card.
💡
All content examples on this page were checked against these limits: the countdown examples (Overview, Anatomy, Mobile Stacking) sit at 93 characters; the no-countdown examples (Content States, the Neutral variant) sit at 105–126 characters — comfortably under both caps.
Behavior

Countdown

Set data-countdown-end (an ISO-8601 datetime) on the banner root and add a .ufs-ann-banner__countdown block with four [data-ann-unit] spans. On load, initAnnCountdown() ticks every second toward that timestamp and freezes at 00:00:00:00 when it's reached — the banner and countdown row stay visible rather than disappearing, avoiding a surprising layout shift or content loss right as a promotion ends.

JS — self-initializing on load
Runs once per .ufs-ann-banner__countdown found on the page, so multiple independent banners/countdowns can coexist.
JS
function initAnnCountdown(countdownEl) {
  var banner = countdownEl.closest('.ufs-ann-banner');
  var end = new Date(banner.getAttribute('data-countdown-end')).getTime();
  var dayEl = countdownEl.querySelector('[data-ann-unit="days"]');
  var hourEl = countdownEl.querySelector('[data-ann-unit="hours"]');
  var minEl = countdownEl.querySelector('[data-ann-unit="minutes"]');
  var secEl = countdownEl.querySelector('[data-ann-unit="seconds"]');
  function pad(n) { return n < 10 ? '0' + n : '' + n; }
  function tick() {
    var diff = end - Date.now();
    if (diff <= 0) {
      dayEl.textContent = '00'; hourEl.textContent = '00'; minEl.textContent = '00'; secEl.textContent = '00';
      clearInterval(timer);
      return;
    }
    var totalSeconds = Math.floor(diff / 1000);
    dayEl.textContent  = pad(Math.floor(totalSeconds / 86400));
    hourEl.textContent = pad(Math.floor(totalSeconds % 86400 / 3600));
    minEl.textContent  = pad(Math.floor(totalSeconds % 3600 / 60));
    secEl.textContent  = pad(totalSeconds % 60);
  }
  tick();
  var timer = setInterval(tick, 1000);
}
document.querySelectorAll('.ufs-ann-banner__countdown').forEach(initAnnCountdown);
⚠️
Accessibility — do not make the countdown an aria-live region. A per-second announcement would be read aloud continuously by screen readers, which is disruptive and effectively unusable. The digits update visually only; screen-reader users still get the surrounding sentence and the link/button, which is the actionable part. This also sidesteps WCAG 2.2.2 (Pause, Stop, Hide) concerns that apply to auto-updating live regions — plain, non-live text isn't subject to that criterion.
Behavior

Dismiss

Clicking .ufs-ann-banner__close fades the banner out and removes it from the DOM. This is session-only — there's no localStorage persistence, so the banner reappears on the next page load. That's a deliberate simplicity trade-off for this first version, not an oversight; per-banner persistent dismissal (e.g. "don't show again for 7 days") is a reasonable future extension if a specific banner needs it.

JS — delegated click handler
One document-level listener handles every banner's close button, so no per-instance wiring is needed.
JS
document.addEventListener('click', function(e) {
  var closeBtn = e.target.closest('.ufs-ann-banner__close');
  if (!closeBtn) return;
  var banner = closeBtn.closest('.ufs-ann-banner');
  banner.classList.add('is-closing');
  document.activeElement.blur();
  banner.addEventListener('transitionend', function() { banner.remove(); }, { once: true });
});
💡
Focus handling on dismiss: if a keyboard user activates the close button, that element is about to be removed from the DOM — leaving focus references dangling. document.activeElement.blur() returns focus to the document body before removal, rather than letting it silently vanish into an unfocused void.
Responsive

Mobile Stacking

Below 768px, the banner switches to a centered column: title (if present), then text, then the countdown, then the link — restyled into a bordered secondary button — each as its own line. No content is duplicated to achieve this: .ufs-ann-banner__content switches to display: contents, promoting .ufs-ann-banner__title/__text/__link to be direct flex children alongside .ufs-ann-banner__countdown (previously a sibling, not nested inside .content) — an explicit order on each then places the countdown visually between the text and the button.

⚠️
Standalone button label: on mobile the link becomes a genuinely independent, focusable <button>-styled element in the tab order — not inline text a screen-reader user encounters mid-sentence. Short labels like "Shop now" or "Let's Do It" can read as ambiguous out of context (WCAG 2.4.4, link/button purpose). If a given banner's CTA label isn't self-explanatory alone, give the link a fuller aria-label (e.g. aria-label="Shop now — 20% off with SPRING20") rather than changing the visible label.
💡
Visual order vs. reading order: the countdown's position between text and button is achieved with CSS order, which only affects visual layout — it does not change DOM/reading order. A screen-reader user still encounters countdown → text → link in source order, not text → countdown → link. Both sequences are independently coherent (WCAG 1.3.2 is about avoiding a genuinely confusing sequence, not requiring visual/DOM parity), so this is treated as an acceptable trade-off rather than a defect — the same pattern commonly used for things like reordering nav items between mobile and desktop.
Internationalisation

i18n & RTL

Every piece of copy is localised through data-i18n hooks resolved at runtime by the page's translation layer — the banner itself hardcodes nothing user-facing beyond the English fallback text, matching the header, hero, breadcrumb and footer. The component is also direction-agnostic by construction: it's plain flexbox with no directional icons other than the symmetric close X, and every offset that matters (margin-inline-start, inset-inline-end, padding-inline) is a logical property, so it all flips automatically under dir="rtl" with no separate override rule needed — unlike the breadcrumb and nav, which needed explicit [dir="rtl"] rules because they used physical left/right properties.
